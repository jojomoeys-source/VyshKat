# ВышКат

«ВышКат» — консольное приложение для учёта транспорта и других вещей кикшеринга. Проект написан на Go.

В программе можно:

- добавлять самокаты, велосипеды и электровелосипеды;
- отправлять транспорт на техосмотр перед добавлением;
- добавлять шлемы и зарядные станции;
- смотреть весь инвентарь;
- считать общее энергопотребление;
- находить транспорт, подходящий новичкам.

При запуске сначала выполняется небольшая демонстрация, а затем открывается интерактивное меню. Поэтому работу программы можно проверить самостоятельно, вводя данные с клавиатуры.

## Запуск

Для проекта нужна установленная версия Go.

Клонировать репозиторий и перейти в его папку:

```bash
git clone https://github.com/jojomoeys-source/VyshKat.git
cd VyshKat
```

Запустить приложение:

```bash
go run ./cmd/vyshkat
```

Запустить тесты:

```bash
go test ./...
```

## Структура проекта

Основные папки проекта:

- `cmd/vyshkat` — точка запуска программы;
- `internal/domain` — модели транспорта и вещей;
- `internal/service` — техосмотр и основная логика парка;
- `internal/app` — демонстрация и консольное меню;
- `internal/di` — создание и связывание зависимостей.

Я разделил проект на пакеты, чтобы ввод из консоли, бизнес-логика и модели не находились в одном файле. `main.go` ничего не рассчитывает: он получает готовые компоненты из DI-контейнера и запускает их.

## Основные модели

В проекте есть три основных интерфейса:

- `InventoryItem` — любой объект с названием и инвентарным номером;
- `TransportItem` — транспорт, для которого известны исправность и оценка простоты управления;
- `EnergyConsumer` — объект, расходующий энергию за сутки.

Транспорт представлен типами `Scooter`, `Bicycle` и `ElectricBicycle`. Все они используют общую структуру `Transport`.

Шлем реализует только `InventoryItem`. Зарядная станция реализует `InventoryItem` и `EnergyConsumer`. Отдельную общую структуру для вещей я не создавал, потому что сейчас у них мало общих данных и она только усложнила бы проект.

## Как работает добавление транспорта

Основная логика находится в `FleetService`.

Когда пользователь добавляет транспорт, происходят следующие действия:

1. `FleetService` передаёт транспорт в `ServiceCenter`.
2. Центр проверяет его исправность.
3. Исправный транспорт добавляется в инвентарь.
4. Неисправный транспорт не добавляется.

Шлемы и зарядные станции добавляются без техосмотра. Инвентарные номера не должны повторяться. Метод `AddItem` также не позволяет добавить транспорт в обход техосмотра.

Для новичков подходит транспорт с оценкой простоты управления не меньше 6. При подсчёте энергии учитываются только объекты, реализующие `EnergyConsumer`.

## Интерактивная часть

После демонстрации запускается `ConsoleApp`. В меню пользователь может добавить объект или запросить один из отчётов.

Консольная часть занимается только вводом и выводом. Например, она считывает название и номер объекта, создаёт нужную модель и вызывает метод `FleetService`. Все основные проверки выполняются не в меню, а в бизнес-логике.

## Dependency Injection

Для DI-контейнера используется библиотека `go.uber.org/dig`. Его настройка находится в `internal/di/container.go`.

Контейнер создаёт:

- центр техосмотра;
- `FleetService`;
- демонстрационный сценарий;
- консольное приложение;
- стандартные потоки ввода и вывода.

`FleetService` получает центр техосмотра через конструктор. Благодаря этому в обычной программе можно использовать настоящий центр, а в тестах — простую подмену с заранее известным результатом.

## SOLID

### Single Responsibility Principle

Я постарался разделить разные задачи по компонентам. Доменные типы хранят данные, `OperationalServiceCenter` проводит техосмотр, `FleetService` управляет инвентарём, а `ConsoleApp` работает с пользователем.

### Open/Closed Principle

Расчёт энергии работает через интерфейс `EnergyConsumer`, поэтому новый потребитель энергии можно добавить без изменения самого расчёта. Аналогично `FleetService` работает с транспортом через `TransportItem`.

Для добавления нового транспорта в консоль всё равно понадобится новый пункт меню, потому что меню должно знать, какие данные спрашивать у пользователя.

### Liskov Substitution Principle

Самокат, велосипед и электровелосипед можно передать в методы `FleetService` как `TransportItem`. Сервису не требуется знать конкретный тип транспорта.

### Interface Segregation Principle

Я не стал делать один большой интерфейс для всех объектов. Интерфейсы `InventoryItem`, `TransportItem` и `EnergyConsumer` разделены, поэтому шлему не нужно иметь ненастоящее энергопотребление, а зарядной станции — свойства транспорта.

Именно этот принцип заметнее всего повлиял на устройство проекта.

### Dependency Inversion Principle

`FleetService` зависит от интерфейса `ServiceCenter`, а не от конкретного `OperationalServiceCenter`. Нужная реализация передаётся через конструктор и связывается DI-контейнером.

## Какой принцип я ограничил

`FleetService` не только добавляет объекты, но и формирует простые отчёты: считает энергию, возвращает количество объектов и ищет транспорт для новичков. Формально эти задачи можно вынести в отдельный сервис.

Я оставил их вместе, потому что приложение небольшое и все эти операции работают с одной коллекцией. Дополнительные сервисы и хранилища здесь сделали бы код сложнее. Если проект станет больше, отчёты и хранение можно будет разделить.

`ConsoleApp` тоже выполняет несколько близких задач: показывает меню, проверяет введённые значения и создаёт доменные объекты. При появлении большого числа команд создание объектов можно вынести в отдельные фабрики.

## Как расширить проект

### Новый вид транспорта

Для нового транспорта нужно создать доменный тип и реализовать `TransportItem`. Если он расходует энергию, ему также нужно реализовать `EnergyConsumer`. После этого останется добавить конструктор, тесты и пункт консольного меню.

Основную логику `FleetService` и техосмотра менять не потребуется.

### Сотрудники

Сотрудник не является инвентарным объектом, поэтому я бы создал для сотрудников отдельную модель и отдельный сервис. Текущую коллекцию транспорта и вещей менять не нужно.

### Несколько складов

Сейчас `FleetService` хранит одну общую коллекцию. Для нескольких складов я бы добавил модель склада и связал каждый объект с конкретным складом. Логику хранения пришлось бы расширить, но модели транспорта и интерфейсы `TransportItem` и `EnergyConsumer` можно было бы оставить без изменений.

## Тесты

Тесты находятся рядом с кодом соответствующих пакетов.

В `internal/service/fleet_service_test.go` есть подмены центра техосмотра:

- `approvingServiceCenter` всегда разрешает добавить транспорт;
- `rejectingServiceCenter` всегда отклоняет его.

Они позволяют проверить `FleetService` отдельно от рабочего центра техосмотра. Тест с названием `TestBeginnerFriendlyTransportsReturnsOnlyTransportsWithScoreAtLeastSix` проверяет границу правила для новичков: оценка 5 не подходит, а 6 уже подходит.

Также тестами проверяются повторяющиеся номера, подсчёт энергии, доменные модели, DI-контейнер, демонстрация и ввод из консоли.

## Использование ИИ

ИИ помогал мне разбираться с синтаксисом Go. Код я писал, запускал и проверял самостоятельно, а непонятные конструкции дополнительно разбирал.
